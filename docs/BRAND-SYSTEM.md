# Gun-metal — the design system

A skeuomorphic system built on machined metal. The brief was gun-metal texture and a
gun-metal grey palette; this is how that was turned into something a page can be
built out of rather than a mood.

Everything lives in `src/styles/`:

| file | what it is | who wrote it |
|---|---|---|
| `tokens.css` | the token layer | generated by `sr-tokens` from the browser capture, plus the gun-metal brand layer appended by `tools/apply-brand-layer.mjs` |
| `fonts.css` | 20 self-hosted `@font-face` rules | generated by `tools/fetch-fonts.mjs` |
| `site.css` | the system | authored |
| `motion.css` | 18 keyframes + the motion inventory | generated by `sr-motion` from live `getAnimations()` |

---

## The four rules

Everything else follows from these. Break one and the page stops reading as metal.

### 1. One light source, upper left

Every raised surface gets a light hairline on its top edge and a dark hairline on its
bottom edge. Every recessed surface gets the reverse. That is the whole illusion. A
border that does not obey it reads as a border, not an edge.

The light model is tokenised so it cannot drift:
`--lite-1 · --lite-2 · --lite-3 · --dark-1 · --dark-2 · --dark-3 · --hairline · --hairline-dk`

### 2. Three plate states, plus glass

| state | token | used for |
|---|---|---|
| raised | `--plate-raised` | buttons, cards, tiles, the logo badge |
| flush | `--plate-flush` | hovered nav items, thumbnails, dividers |
| sunk | `--plate-sunk` | inputs, the product stage, icon wells, the ticker |
| lifted | `--plate-lifted` | things above the page: mega panels, the hero, hover |

Inputs are **always** sunk — a hole is where you put something. Buttons are raised
until `:active`, when they travel 1px and swap to sunk. That 1px is the entire
difference between a button that looks pressable and one that looks printed.

### 3. No colour literals outside the token layer

`site.css` contains **zero** hex, `rgb()` or `hsl()` values — 699 `var()` references
and nothing else. Even the translucent light-model values are tokens. Retune the
palette in `tokens.css` and the whole site moves together.

This is enforced: gate check C13 fails the build if authored CSS carries more colour
literals than token references.

### 4. Glass floats, metal is the chassis

Glassmorphism and skeuomorphism are opposite material languages — translucent and
blurred against opaque and machined. They are reconciled here by making glass a
**pane laid on the metal**, never a replacement for it.

Glass is only for surfaces that FLOAT with something behind them worth glimpsing:

| glass | why |
|---|---|
| `.masthead` | sticky at top:0 with the whole document scrolling under it |
| `.facets__panel` (desktop only) | absolutely positioned over the product grid |
| `.agegate` scrim | the storefront frosts behind it; its panel stays metal |
| `.lightbox::backdrop` | the page frosts behind the light table |
| `.cartnote__panel` | slides in over scrolling content, at the LITE blur |
| `.stickybuy` | fixed over the product page |
| `.hero__eyebrow` | one pill sitting on the photograph |
| `.btn--ghost` | it already declared itself transparent |

Everything else stays opaque metal. Four surfaces **must never** be glass:

- **`.pcard__media`, `.pdp__stage`, `.lightbox`** — their images use
  `mix-blend-mode: multiply` against an opaque light box. Make the parent
  translucent and every product cut-out multiplies against the dark page and goes
  near-black. `site.css` already records this exact failure for `.pdp__thumbs`.
- **`.disclaimer`** — the block with legal weight. Legibility is not negotiable.
- **`.nav__panel`** — it is a DOM descendant of the glass `.masthead`. An element
  with a `backdrop-filter` becomes a Backdrop Root, so a descendant can only sample
  what that root painted; the panel hangs below the masthead's box, where that root
  painted nothing, and would blur an empty backdrop into a flat tinted rectangle.
  **Glass rail, machined drawer** — you cannot have both.
- **`.tile`, `.pcard`, `.badge`, `.chip`, `.footer`** — all sit in normal flow on
  the page background with nothing behind them. Blur there is cost with no effect,
  and a collection page carries up to 82 cards.

Three more traps, all avoided in the CSS and worth keeping avoided:

- The blur is **fallback-first**: the base rule is the no-backdrop-filter surface
  (`--glass-tint-solid`, contrast-identical to a real card) and the blur is added
  inside `@supports`. Never the other way round — an engine that drops the filter
  then inherits a readable pane rather than a transparent one.
- The tint is **dark** (`--gm-800`), not white. Over the dark shell it composites
  darker still, so accent text gains contrast on glass rather than losing it. A
  white tint would have killed `--acc-hi` text above about 8% alpha.

  There are four alphas, and the spread is the whole point — a pane's tint is set
  by **what can pass behind it**, never by taste:

  | token | alpha | used by | why |
  |---|---|---|---|
  | `--glass-tint` | 0.39 | cards, tiles, facets, badges, ghost buttons | sits on the dark page; nothing bright ever passes behind |
  | `--glass-tint-deep` | 0.56 | panels stacked over other glass | one layer of glass is already behind it |
  | `--glass-tint-rail` | 0.78 | `.masthead` only | sticky over the **entire document**, white product photography included |
  | `--glass-tint-solid` | 0.94 | every no-`backdrop-filter` fallback | nothing is blurred behind it, so the pane must carry its own legibility |

  The rail is not a style choice. Measured over a `--gm-050` product media well
  scrolling underneath, the nav read **1.58:1** at 0.39. `tools/solve-tint.mjs`
  solves the floor at 0.72; the rail takes 0.78 for headroom.
- **Never** `will-change` or `contain: paint` on a glass ancestor. Both create a
  containing block for `position: fixed`, which would re-anchor `.stickybuy`,
  `.cartnote` and `.agegate` and re-break the mega-panel overflow fix. The blur is
  already GPU-composited; the hint buys nothing and costs three working components.

Two blur strengths exist because they have to. `--glass-blur` is 14px, not something
showier: `body` sets `background-attachment: fixed`, and a heavier blur flattens the
`--sheen` wash to a dead tone, at which point the pane stops parallaxing and the
glass reads as a flat grey rectangle. `--glass-blur-lite` (8px) is for
`.cartnote__panel`, which paints over the already-blurred masthead: at full strength
the two compound into exactly the milky blob glass is supposed to avoid.

That 14px blur has one consequence worth knowing when tuning a card: it pulls light
in from **outside** the pane. A card sitting on the dark page computes to 4.95:1 for
`--gm-300` vendor text, but measures 4.48:1 in place, because the white media well
directly above bleeds into the blur. That is why `.pcard__vendor` is `--gm-200` and
not the `--gm-300` the palette would suggest — a real measurement beat the
arithmetic, and the arithmetic was the thing that was wrong.

blue-grey with a faint green cast. That cast is what separates gunmetal from a
neutral grey, and it is why the page does not look like a generic dark theme.

### The accent is EMERALD (revised)

The hue lives in **one token**, `--acc-rgb: 7 115 74`, and `--acc-glow` and
`--glass-acc-edge` derive from it — so retuning the brand is one line rather than a
hunt through rgba() literals.

```
--acc-deep  #065f3d   button hover
--acc       #07734a   button at rest
--acc-hi    #0ab875   LINK AND PRICE TEXT, and the 1px button rim
--acc-lo    #034e32   button pressed
```

This is a **deliberate brand change**, not a lost measurement. The yellow-green the
live site actually used is still recorded where `sr-tokens` wrote it, as `--c-2:
#74a739` — the capture is intact.

The change also fixed a real accessibility defect. Every pairing below was computed
with `node tools/contrast.mjs`, never estimated:

| pairing | before | after |
|---|---|---|
| white text on the button at rest | **4.30:1** | 5.62:1 |
| white text on the button on hover | **2.73:1** | 5.62:1 — the fill no longer moves |
| white text on the button on hover, reduced motion | **2.73:1** | 7.38:1 |
| white text on the button pressed | 4.30:1 | 9.36:1 |
| `--acc-hi` on a card | 8.33:1 | 6.51:1 |
| `--acc-hi` on `--gm-700` (`.brand__mark`, the binding case) | 6.9:1 | 5.55:1 |

Both button states failed AA before. Two constraints make the window narrow: white
text needs the fill DARK, and WCAG 1.4.11 needs the fill distinguishable from the
page. Lightening on hover is impossible here — a lighter emerald measures 4.13 and
3.45 under white text. The resolution is that **the fill does not change on hover at
all**: a metal shimmer sweeps across the face instead (see *Motion*), so the rest
contrast is also the hover contrast and the narrow window never has to be crossed.
Under `prefers-reduced-motion` the sweep is suppressed and the button falls back to
darkening, which raises contrast rather than lowering it.

The fill alone only reaches 2.85:1 against a card, so the button carries a **1px
`--acc-hi` rim**, which measures 5.55–7.54:1 against every surface it lands on and
satisfies 1.4.11 by boundary.

`--brass` is used sparingly, for engraved rules and badge rims.

## Surfaces

Two gradient tokens do the material work, and neither costs a request:

- `--sheen` — a vertical light-to-dark wash with a hard break at 42%, which is where
  a flat metal panel catches the room.
- `--knurl` — crossed 45° repeating gradients. The grip texture, used on the logo
  badge and the lower edge of `.btn--knurled`. This is the **only** repeating
  gradient still painted anywhere; `tools/probe-texture.mjs` asserts that, and its
  `--control` flag proves the assertion is not a blind one.

### Retired: `--grain` and `--glass-noise`

Both were 4px repeating linear gradients — the brushed machining on the body, the
plates and the masthead, and a matching tooth on the glass. They are now `none`.

They are **retired rather than deleted**, and they are still referenced at 22 and 6
call sites. `none` is a valid `background-image` *layer*, so a declaration written
`background-image: var(--grain), var(--sheen)` still resolves — it simply paints an
empty layer above the sheen. Restoring the roughness is one token value; no authored
stylesheet has to change either way. Deleting the tokens instead would have meant
editing 28 call sites to take an effect out that may be wanted back.

`.plate--riveted` adds four machined screw heads with a radial gradient, for panels
that should read as fastened down (the age gate, the basket notification).

### Generated imagery

24 images in `src/assets/generated/`, made with fal.ai (`fal-ai/flux/dev`), each with
its full prompt, seed and model recorded in `provenance.json`. Six are seamless metal
textures, one is the hero plate, seventeen are product-category stills.

**Every one was looked at.** They were rendered to labelled contact sheets
(`audit/contact-sheets/`) and read by eye, because a text or alt check cannot see a
fabricated wordmark. That pass rejected or regenerated six:

- `tex-knurled-grip` rendered a **handgun**, because the shared style string put
  "gunmetal" next to "grip". Regenerated with a style override containing no
  weapon-adjacent vocabulary.
- `cat-disposable-vapes`, `cat-wax-pens` and `cat-accessories` carried invented
  lettering on the products. Regenerated.
- `cat-glass-pipes` and `cat-glass-bangers` never resolved as their category and are
  **rejected** — `provenance.json` marks them so, and `generate.mjs` cannot publish a
  rejected image. Glass categories use the client's real product photography.

The verdict for each image is in `provenance.json` under `inspectionVerdict`.

## Motion

### Button hover is a metal shimmer, not a colour change

A machined face does not change colour when you approach it — it catches the light.
So `.btn` holds its fill on hover and a specular band sweeps across it instead.

The band is a `::before` at `z-index: -1`. That negative index is doing real work:
`.btn` is `position: relative` with no `z-index`, so a positioned pseudo would paint
*above* the label. `isolation: isolate` makes the button a stacking context, which
lets the pseudo sit at `-1` and travel **between the fill and the text**. `isolation`
was chosen deliberately over `will-change`, `contain`, `filter` or `transform` — it
creates a stacking context but **not** a containing block, so nothing `position:
fixed` on this site gets re-anchored by it. `overflow: hidden` was already on `.btn`,
so the skew never leaks past the corner radius.

It animates `transform`, not `left`, so the sweep stays on the compositor and costs
no layout on a page that can carry 82 buttons. `.btn--primary` takes a second,
narrower band on `::after` at a 0.12s delay, so the brand control reads as the most
polished surface on the page. A `.btn--primary.btn--knurled` keeps its grip strip and
takes only the single band — `::after` is already spoken for there.

Under `prefers-reduced-motion` both bands are suppressed, and the old colour shift
comes back, because hover still needs *some* affordance.

Verified by `tools/probe-shimmer.mjs`, which reports `sr-btn-shimmer running on
::before` and `fill stays put: yes`. It deliberately selects a **visible** match:
the first `.btn--primary` in the DOM is inside the `display: none` age gate, where a
percentage transform resolves to `none` and a working rule reads as broken.

### Scroll reveals

`IntersectionObserver`, one-shot (`unobserve` on entry), `rootMargin: 0px 0px -8% 0px`
so a card commits just before its top edge lands. Cards, tiles, badges, section heads
and prose carry `data-reveal` with a `--i` stagger.

It is progressive enhancement in the strict sense: the hiding rule is scoped to
`html.js-reveal`, and that class is added **only** by script, only after confirming
`IntersectionObserver` exists and reduced-motion is off. No JS, old engine, or
reduced-motion preference means no hidden content — not hidden content that never
comes back.

### The FAQ accordion slides

A native `<details>` snaps, and CSS alone cannot fix that: the content is not in
flow until `open` flips, so there is nothing to interpolate between.
`src/scripts/accordion.js` measures the closed and open heights and animates the
box between them — **620ms** opening, **540ms** closing, on
`cubic-bezier(0.22, 0.61, 0.36, 1)`. Closing is the quicker of the two because a
panel that lingers on the way out reads as lag rather than as motion.

`::details-content` plus `interpolate-size: allow-keywords` would do this with no
script and is the nicer answer — but only where both have shipped, which would give
the client the effect in some browsers and not others. The script route works
anywhere `Element.animate` does, and where it does not run at all the accordion is
simply native.

Two details that are easy to get wrong:

- `open` must stay **true** for the whole collapse, or the content vanishes on the
  first frame and there is nothing left to slide. That is why `.is-closing` exists:
  it flips the +/- marker and the summary colour immediately, so the control feels
  responsive while the panel is still visibly closing.
- Reduced motion is honoured by **not intercepting the click**, so those visitors
  get the browser's own instant toggle rather than a re-implementation of it.

`tools/probe-accordion.mjs` samples the height every frame: 26 distinct heights
expanding, 23 collapsing, visible movement settling around 517ms / 450ms (the tail
of the easing moves sub-pixel). Its control runs the same clicks under
`prefers-reduced-motion: reduce` and requires a **snap** — one height, 0ms.

### The vapour field

A drift of five soft plumes behind the whole site, fixed at `z-index: -1`.

**The cost is not the effect — it is what the effect makes the rest of the page
redo.** This page carries **90 elements with a `backdrop-filter`**, 78 of them
product cards, with 8 on screen at a time covering ~66% of the viewport. Anything
that changes behind them forces every one to re-sample. That ruled out a canvas
(a new bitmap every frame across the full viewport), an animated `filter`, and an
SVG `feTurbulence`.

What is left is the cheapest thing that can carry it: three **real smoke plates**,
rasterised once and moved with **nothing but transform**, so the drift stays on the
compositor. There is no blur filter anywhere in it.

**Gradients were tried first and they do not work.** Soft radial ellipses rendered,
moved, measured and bounded correctly and still did not look like smoke, because a
gradient is a haze and smoke is *wisps*. No amount of tuning an ellipse produces a
tendril — the shape has to come from an image. The plates are generated (fal), then
converted by `tools/smoke-plate.mjs`, which crops, turns luminance into alpha, and
feathers all four edges.

Three things that tool exists to handle, each from a real defect:

- **Crop.** Two of the three generations put a lit floor — and in one case an
  incense holder — in the bottom of the frame, despite the prompt excluding them.
  Regenerating with explicit negatives produced the object again; flux does not
  honour negative prompts. The raw plates therefore carry `inspectionVerdict:
  not-published` and only the cropped derivatives ship.
- **Luminance to alpha.** White-smoke-on-black cannot be used directly: the black
  paints as a black rectangle. A blend mode would fix that only where no ancestor
  happens to form a stacking context, which is not a property worth depending on,
  so the transparency is baked into the file.
- **Feather.** A crop leaves a hard edge, and a hard edge on a drifting plume reads
  as a sliding rectangle.

The plates are `--vapor-1/2/3`, still tokens, so no plume rule changed when the
gradients were replaced. `sr-rebase` hoists a `url()` inside a custom property into
its own sheet deliberately — Chrome resolves it against the consuming sheet and
other engines against the declaring one.

**The hero's plumes sit at `z-index: -1`, the same index as the scrim, not 0.**
Among positioned elements sharing an index the painting order is DOM order, and
`::after` is the hero's last child, so the scrim lands on top of the smoke. That is
load-bearing: the scrim is what makes the headline readable, and with the plumes
above it the h1 measured **2.04:1 against a 3:1 floor**. Underneath it the smoke
still reads at full strength on the image side, where the scrim is transparent.

**Phone widths drop one plume and repoint the rest.** The three plates cost 142KB —
27% of a phone's initial payload. At ≤767px the heaviest plate is not referenced by
any visible element, and a `background-image` on a `display: none` element is never
fetched, so it is not downloaded at all rather than merely unused: **521KB → 454KB**.
Measured against the pre-vapour baseline on the 82-card collection page: mean
16.67ms before and after, p95 16.8ms, **0 long frames** either way, at 1440px and
390px alike.

The plume fills live in `tokens.css` as `--vapor-1/2/3` because C13 holds authored
sheets to zero colour literals and a radial gradient is a pile of them.

**Bounds are proven, not calculated.** A plume's rect includes its transform, and
a closed-form estimate of it was wrong: a rotated box measures `w·cos + h·sin`, and
because the widths here are `vw` while the heights are `vh`, the overflow grew as
the viewport *narrowed* — the opposite of what a vw-only model predicts. It reached
33px past the viewport at 390px. `tools/probe-vapor-bounds.mjs` steps every plume
through a full cycle at all four breakpoints and reports the widest rect; run it
after changing any size, offset, scale or rotation.

`tools/probe-vapor.mjs` covers the rest: that all five animations are *running*,
that the field is behind content and eats no clicks, and that it changes real pixels.
Its reduced-motion control requires **0** changed pixels — which is what proves the
movement is the animation and not noise.

**The hero carries its own plumes.** The site-wide field sits behind the page, so
any opaque section hides it — and the hero is both opaque and full-bleed, which meant
the first screen had none at all. Measured at 1563x653: scrollY 0 changed 0.5% of
pixels with a peak delta of 6, against 6.7–16.8% everywhere below it. `.hero__vapor`
sits at `z-index: 0`, above the photograph (`-2`) and the scrim (`-1`), with
`.hero__inner` promoted to `z-index: 1` so the headline is always in front of the
smoke. `.hero` already carries `isolation: isolate`, which is what makes those
negative indices resolve inside it.

Those plumes are sized in percentages of the hero, and **their bounds still had to be
proven** — the same rotation term bites here and harder, because they are a large
fraction of the hero's height and rotation turns height into width. The first
version ran 100–256px past the viewport at every breakpoint.

**Visibility is its own check, separate from movement.** `tools/probe-vapor-visible.mjs`
renders each frame with the field and without it and counts the pixels that differ,
which is the only question that matches "I can't see it". A plume can be running,
fast, in-bounds and still invisible. Current readings: **19.8–28.1%** of pixels at
the top of the page, **6.8–20.6%** on mobile, peak deltas 51–166.

**Speed is its own check, and this is why.** The first version ran on 56–97 second
cycles and travelled about **7px per second** — under the speed at which the eye
registers motion at all. Every probe passed: the animations were running, the plumes
were bounded, pixels differed between screenshots. It was green and invisible,
because "do pixels change over five seconds" tests whether an effect EXISTS, not
whether anyone can see it. Those are different questions and only one of them was
being asked.

Cycles are now 24–41s over ~88vh of travel, which `tools/probe-vapor-speed.mjs`
measures at **19–34 px/s, mean 27**. It holds the band at 10–60 px/s: below 10 reads
as a still image, above 60 an ambient background starts competing with the content.
Horizontal travel was deliberately left alone when speeding this up, because the
proven bounds depend on it — vertical travel is clipped and free.

One cascade trap, worth keeping in mind before adding a hover rule: the settled
reveal state `.js-reveal [data-reveal].is-in { transform: none }` is specificity
0,3,0 and beats a plain `.pcard:hover` at 0,2,0. Hover rules that move a revealed
element must match that specificity and come later, or the lift silently dies while
the image scale and glare still fire — which looks like a half-broken component
rather than a cascade bug. `tools/probe-hover.mjs` measures all four hover effects
separately for exactly this reason.

### `.marquee` — the Best Seller carousel

An infinite strip, no card and no background, sitting directly below the hero.

**The loop is seamless only because the arithmetic is exact.** It translates a
doubled track -50%, which lands on the second copy's first item only if the track is
a whole multiple of the item pitch. `gap` breaks that — 14 items have 13 gaps, so the
track is `14C + 13G` and -50% stops half a gap short, jumping 16px every cycle,
forever. A trailing margin on each card gives `14(C + G)`, whose half is exactly the
eighth card. Change the card width, the margin or the item count and re-run
`tools/probe-marquee.mjs`, which checks the geometry **and** compares the rendered
first and last frames.

**It is a real scroller, not `overflow: hidden`.** Two reasons. The responsive sweep
exempts elements inside an `overflow-x: auto` container, because content wider than
the viewport is the whole point of one — without it, every card past the fold counted
as an element overflowing the page, 64 majors. And it makes the off-screen products
*reachable*: hover pauses the loop and a trackpad or keyboard can then scroll to any
of them, where `hidden` left them reachable only by waiting.

**The title is 19px/700 for a measured reason.** Unboxed text sits directly over the
drifting smoke — 12.72:1 with the field hidden, but 2.49:1 with a bright wisp behind
it. A halo barely helped, because the probe samples the whole line box including the
gaps a soft shadow cannot reach, and white type still left one phase at 4.33:1. At
19px/700 this is WCAG's large-text class with a 3:1 floor, and that same worst phase
measures 4.33. Shrink it, lighten it or drop the weight and that margin goes with it.

There is deliberately **no edge-fade mask**: a mask that fades the ends fades the
text in them too, and partially transparent body text is partially readable text.

**The products float because the white is out of the pixels, not just the CSS.**
`tools/cutout.mjs` flood-fills the studio background from the frame border — not a
white key, which would punch holes through the products that are themselves white
(the Elements box, the pale Blazy Susan packaging, the lighter display's labels).
Filling only what is *connected to the edge* leaves enclosed white alone. The tool
refuses any image whose border is not flat, or where the fill takes under 3% or over
92% of the frame, and the original photograph is kept instead.

Two rules for re-cutting: judge the result composited on the **page colour**, never on
white, or a white fringe is invisible; and downscale **after** the fill, never before,
because on an interpolated image the product/background boundary is a gradient that
the fill either leaks through or stops short of. They are capped at 700px — ample for
a 210px card at DPR 3 — because alpha costs bytes. Altered client imagery is recorded
in `audit/cutouts.json`; the originals still serve every product page and grid.

**The centre card is enlarged by `src/scripts/marquee-focus.js`.** An
IntersectionObserver whose `rootMargin` collapses the strip to a band down its middle
gives membership; the *choice* among the one or two cards in that band is re-made on a
frame loop, because the observer only speaks on threshold crossings and a card
otherwise holds the highlight up to 168px past centre. Only `transform` and `opacity`
animate, and the dimming is on the **picture only** — never the title or price, which
carry a contrast floor with no panel behind them.

### `.brand--markonly` — two things that must stay true

**Both** brand links — masthead and footer — are the logo alone, because the wordmark
is already drawn inside the logo artwork and setting it again as text said the same
thing twice.

The footer was worse than redundant. With the alt text and the visible text both
present, its accessible name computed to **"Smoke Shop Guru Smoke Shop Guru
ALBUQUERQUE, NM"** — the name announced, then announced again. Mark-only leaves one
clean name, and the tagline paragraph beneath still identifies the block.

Removing the visible text takes away two things the markup was getting for free:

- **The accessible name.** It now comes entirely from the `<img alt>`, which is the
  brand name verbatim. Chrome's accessibility tree reports role `link`, name
  `"Smoke Shop Guru"`, computed from contents. Blank that alt and the header's
  home link becomes an unnamed link. `tools/probe-brand-a11y.mjs` asserts it.
- **The tap target.** The link used to be a logo stacked with two lines of text, so
  it cleared 44x44 by accident. Mark-only it measured **191.4x40** at 390px — six
  MAJOR findings in the responsive sweep. `min-height: 44px` on the link restores
  the target without changing the logo's drawn size.

The logo has **no plate**: the file carries a real alpha channel, so the white card behind it was CSS — a background, padding and a bevel, all removed. The heights now describe the ARTWORK, not a padded box: `height: 48px` (38.4px below 560px), which is the old 40px and 32px of drawn logo plus 20%. The `<img>` declares
**261x66**, the file's real dimensions read from the WebP header, rather than the
120x30 it declared before — a 4.000 ratio against the file's actual 3.955. Enlarging
it cost no layout: the masthead measures **72px** tall whether the drawn logo is 34px
or 48px, because the bar's height is set by the nav controls, not by the mark.

## Responsive

Breakpoints are the measured ones: **390 / 768 / 1024 / 1440**. The design baseline
was captured at all four, on six representative pages.

The nav collapses to a checkbox-driven drawer at 1023px and needs no JavaScript. The
accordions are `<details>`. The only things that need script are the age gate, the
basket, the facets, search and the lightbox — the page is readable and navigable
with all script blocked.
